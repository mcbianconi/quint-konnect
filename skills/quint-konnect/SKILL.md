# quint-konnect: model-based testing for Kotlin

quint-konnect replays execution traces generated by the `quint` CLI against a Kotlin driver
class to verify the implementation matches its Quint spec. Data flow:

```
Quint spec (.qnt) -> [quint CLI] -> ITF trace files -> quint-konnect -> your Kotlin code
```

This skill covers wiring an *existing* `.qnt` spec to Kotlin. It does not cover writing or
modeling the spec itself — see "Spec authoring" at the end.

## 1. Prerequisites

- JDK 21.
- `quint` on `PATH`, matching version **0.32.0** (`quint --version`). Install/upgrade with
  `npm i -g @informalsystems/quint@0.32.0`.
- A Kotlin/Gradle project with a Kotlin JVM module (or one you're adding).

## 2. Gradle setup

Read `references/gradle-setup.md` for the full snippets (Gradle plugin path and a manual
fallback) before writing any build file — it has the exact dependency coordinates, the
`pluginManagement` block the plugin needs, and the KSP generated-source-dir wiring. In short:

- Prefer applying the Gradle plugin, id `io.github.mcbianconi.quint-konnect`. It applies KSP,
  adds the `kspTest`/`testImplementation` dependencies, wires the generated test source
  directory, and adds a `checkQuint` task that fails the build if `quint` is missing.
- Without the plugin, apply `com.google.devtools.ksp` yourself, add
  `kspTest("io.github.mcbianconi:quint-konnect-ksp:<VERSION>")` and
  `testImplementation("io.github.mcbianconi:quint-konnect-core:<VERSION>")`, and wire
  `build/generated/ksp/test/kotlin` into the `test` source set.
- quint-konnect isn't on Maven Central yet: use `<VERSION>` as a literal placeholder and ask the
  user what version/local-build mechanism (`includeBuild`, `publishToMavenLocal`) they're using.
- A driver's spec file and its Kotlin driver class both live under `src/test/`, not `src/main/`
  (drivers are test code; only the plugin wires `kspTest`, not `ksp`).

## 3. Map spec actions to a driver

A **driver** is a class implementing `Driver` (from `quint-konnect-core`), annotated with
`@QuintRun` (traces via `quint run --mbt`) or `@QuintTest` (traces via `quint test --match`).

```kotlin
import io.github.mcbianconi.quintkonnect.Driver
import io.github.mcbianconi.quintkonnect.State
import io.github.mcbianconi.quintkonnect.annotations.QuintAction
import io.github.mcbianconi.quintkonnect.annotations.QuintRun

@QuintRun(
    spec = "src/test/resources/tictactoe.qnt",
    maxSamples = 5,
)
class TicTacToeDriver : Driver {
    val game = TicTacToe()

    override fun quintState(): State<TicTacToeDriver> = TicTacToeState()

    @QuintAction("init")
    fun init() {
        game.board.forEach { row -> row.fill(null) }
        game.nextTurn = Player.X
    }

    @QuintAction("MoveX")
    fun moveX(corner: List<Long>?, coordinate: List<Long>?) {
        val coord = (corner ?: coordinate)?.let { Pair(it[0], it[1]) } ?: Pair(2L, 2L)
        game.movePlayerTo(Player.X, coord)
    }

    @QuintAction("MoveO")
    fun moveO(coordinate: List<Long>) {
        game.movePlayerTo(Player.O, Pair(coordinate[0], coordinate[1]))
    }
}
```

Rules for this shape:

- **One `@QuintAction("Name")` per spec action**, including `init`. `Name` must match the
  Quint action name exactly (case-sensitive); `@QuintAction()` with no name falls back to the
  Kotlin function's own name, so name it to match if you'd rather not repeat the string.
  `@QuintAction` functions must be `public`.
- **Parameters are nondet picks**, matched to `mbt::nondetPicks` **by Kotlin parameter name**
  (not position). A parameter's type follows the same table as spec state
  (`references/types.md`) — e.g. a Quint tuple pick is `List<Long>`.
- **Nullable parameter type (`T?`) = optional pick.** Some `quint run` steps don't set every
  nondet variable (e.g. a branch that doesn't call `oneOf()` this step); a non-nullable
  parameter for a pick that's absent that step throws `Missing required nondet pick '<name>'`
  at replay time, so only declare a parameter non-null if every action invocation truly sets it.
- **No `override fun step(...)` needed.** `Driver.step`'s default implementation finds the
  KSP-generated dispatcher (`generatedStep`) by the driver's class name and calls it. Only
  override `step` for genuinely custom dispatch.
- **`quintState()` must return `State<YourDriverClass>`**, not `State<*>` — KSP reports a
  compile error otherwise (it validates the return type against the driver class).
- **`@QuintAction` functions may be `suspend`.** The generated dispatcher runs them with
  `kotlinx.coroutines.runBlocking`, so the driver's module needs `kotlinx-coroutines-core` on
  its test classpath (see `references/gradle-setup.md`) — KSP reports a clear error naming the
  missing dependency if it isn't resolvable, rather than failing with an obscure "unresolved
  reference" in generated code.
- **The driver needs a public no-arg constructor.** The generated test factory instantiates a
  fresh driver per trace.

### `@QuintTest` also needs `nondetPath`

`quint test` (the CLI's test-runner, as opposed to `quint run`) has no `--mbt` flag, so its
traces carry no `mbt::actionTaken`/`mbt::nondetPicks`. A `@QuintTest` spec must instead model
the action taken as its own sum-type variable, and the driver must point `config()` at it:

```kotlin
@QuintTest(spec = "src/test/resources/quinttest/counter.qnt", test = "happyTest")
class CounterDriver : Driver {
    var count = 0L
    override fun config(): DriverConfig = DriverConfig(nondetPath = listOf("lastAction"))
    override fun quintState(): State<CounterDriver> = CounterState()

    @QuintAction("Init")
    fun init() { count = 0 }

    @QuintAction("Add")
    fun add(n: Long) { count += n }
}
```

The matching spec side:

```quint
type Action = Init | Add({ n: int })
var lastAction: Action
action add(n) = all { count' = count + n, lastAction' = Add({ n: n }) }
```

`@QuintAction` names here are the sum type's variant tags (`"Init"`, `"Add"`), and
`nondetPath` is the dot-path to the variable holding it. Without this, `@QuintTest`'s default
`DriverConfig()` doesn't work — see
`docs/decisions/quint-test-needs-nondet-path.md` in the quint-konnect repo for why.

## 4. Check state (optional, but recommended)

Give the driver a `TypedState`: a `@Serializable` data class mirroring the spec's own state,
decoded from the ITF trace and compared field-by-field against the implementation after every
step.

```kotlin
@Serializable
data class MySpecState(val count: Long)

class MyState : TypedState<MyDriver, MySpecState>(serializer()) {
    override fun extractFromDriver(driver: MyDriver): MySpecState =
        MySpecState(count = driver.counter)
}
```

A mismatch names the differing field, e.g. `cells.(1, 2): spec="X", impl="O"`; sets compare
regardless of order. See `references/types.md` for the full Quint-to-Kotlin type table
(sum types, tuples, maps, `Option`, oversized integers).

- Mark a field the implementation doesn't track with `@QuintIgnore` (from
  `quint-konnect-annotations`) — it still has to decode, so give it a default (or make it
  nullable) if the spec might omit it; a mismatch on it never fails the check.
- Override `TypedState.compareField(path, spec, impl)` for a field that needs its own
  comparison logic; return `null` to fall through to the default structural comparison.
- If the driver doesn't return a real `State`, the default `quintState()` skips state checking
  entirely — the run still replays actions, it just never compares state.

## 5. Run and debug

```bash
./gradlew :mymodule:test
```

Each generated `@QuintRun`/`@QuintTest` test class exposes one JUnit 5 **dynamic test per
trace**, named `trace <n> (seed <seed>)`. The seed is for the whole run (one `quint` invocation
that emits several traces), not per trace — every dynamic test in a run shares the same seed,
and "trace N" is just that trace's index within the run.

Environment variables:

| Variable | Values | Effect |
|---|---|---|
| `QUINT_SEED` | hex, e.g. `0xdeadbeef` | Fixes the seed for reproduction. Only takes effect if the driver's `@QuintRun`/`@QuintTest` doesn't set its own `seed = "..."` — an explicit annotation seed always wins. |
| `QUINT_VERBOSE` | `1`, `2` | `1` logs each trace/step; `2` also dumps raw ITF state. Goes to stderr. |
| `QUINT_COLOR` | `always`, `never` | Forces ANSI colour on/off. |
| `NO_COLOR` | any non-empty value | Disables colour (https://no-color.org). |

A step or state mismatch throws an `AssertionError` naming the trace, step index, action, and
any nondet picks for that step, e.g.:

```
Failure in trace 2, step 3, action 'MoveX'
Nondet picks:
+ coordinate: (1, 1)
State invariant failed:
--- specification
+++ implementation
...
```

Debugging notes:

- **Read the seed from the failing dynamic test's name** (or the `Reproduce this error with
  QUINT_SEED=0x...` line printed to stderr), then rerun with that `QUINT_SEED` plus
  `QUINT_VERBOSE=2` to see every step leading to the failure.
- **Gradle hides test stderr by default.** `QUINT_VERBOSE` output and the seed-reproduction
  line both go to stderr; without `testLogging { showStandardStreams = true }` (or an
  equivalent IDE setting), you won't see them in the console — check
  `build/test-results/test/*.xml` instead, or add that block.
- **A green `test` task is cached (`UP-TO-DATE`)** and won't regenerate traces on a rerun; use
  `./gradlew test --rerun` to force fresh random traces (irrelevant when `QUINT_SEED` is set).
- **Fix the implementation, not the spec**, unless the spec itself is wrong — the whole point
  of the exercise is checking the implementation against the spec, not the reverse.
- An **anonymous action** (a spec action `quint` can't name, e.g. from an unnamed `any`/`all`
  branch) fails immediately with "An anonymous action was found!" — name every action in the
  spec.
- `error("Unimplemented action: <name>")` at runtime means an action name in the trace has no
  matching `@QuintAction` on the driver, or the name doesn't match exactly (case-sensitive).

## Known limitations

- Not yet published to Maven Central — every dependency coordinate needs the `<VERSION>`
  placeholder resolved by hand for now.
- No Windows support.
- No compile-time check that a `@QuintAction` name or nondet parameter name actually exists in
  the spec — a typo only surfaces when a trace is replayed.
- No runtime override for annotation parameters beyond `QUINT_SEED`; everything else
  (`spec`, `maxSamples`, `maxSteps`, ...) is fixed at compile time in the annotation.
- A failing trace isn't saved anywhere, and there's no ready-made command to replay just that
  trace — reproduce with `QUINT_SEED` and rerun the whole test instead.
- No way to replay a saved `.itf.json` trace without invoking `quint` again.
- No trace shrinking: a failing trace is whatever length `quint run`/`quint test` produced.
- Traces within a run replay sequentially, not in parallel.
- No support for `quint run --invariant` / invariant-violation reporting.
- JUnit 5 only (no runner-neutral adapter yet).

## Spec authoring

This skill assumes the `.qnt` spec already exists. For writing or modifying a Quint spec — the
language itself, `nondet`/`oneOf`, invariants, actions — use a dedicated Quint-language skill if
one is available (e.g. the `quint-lang` skill from Quint's own LLM kit,
github.com/quint-co/quint-llm-kit) rather than improvising the language here.
