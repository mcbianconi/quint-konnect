# Feature: Post-0.2.0 assessment fixes

**Date:** 2026-09-28 (last updated 2026-09-28)

**Author:** Murillo Cesar Bianconi, with Claude

**Status:** Draft

## Overview

A project assessment of `main` at `aa80813` (tag `v0.2.0`) found one high-severity bug, two
medium-severity problems and some low-severity problems. Most of them come from qk-adm2, which
moved trace generation into the Gradle task `generateQuintTraces`. This spec plans the fixes.
Each item below has one bead. The epic is qk-c7mu.

This spec uses ASD-STE100 (Simplified Technical English) style.

## Goals

- An incremental build never replays traces of an old spec.
- A driver replays only its own traces.
- A filtered test run (`--tests`) runs quint only for the drivers that it tests.
- Every quint process that the plugin starts has a time limit.
- One implementation (or a parity test) builds the quint command line.
- The library has fewer options that do nothing.
- The docs agree with the code.

## Non-Goals

- ktlint tooling (qk-sc8x).
- A Kotest adapter.
- Windows support (`docs/decisions/no-windows-support.md`).
- A wider scope for the spec checks of qk-75ad (`@QuintTest`, drivers that override `config()`).
- The README rewrite itself (qk-6fru). qk-6fru waits for B3 and B6, because they change the
  options that the README describes.

## Background

The assessment read all the main source code and compared the 89 closed beads with the code.
`./gradlew build` passed (389 tests, 0 failures). CI passed on `aa80813`. Three findings were
confirmed with a manual test on `example/`:

1. **Stale traces.** With `-Pquint.seed=0x1`, `InvariantCounterDriver` passed. Then the spec
   `example/src/test/resources/invariants/counter.qnt` changed from `n' = n + 1` to
   `n' = n + 2`. The same command ran `quintIr` and `kspTestKotlin` again, but
   `generateQuintTraces` was UP-TO-DATE and the test passed. With
   `generateQuintTraces --rerun`, the test failed with `n: spec=2, impl=1`.
2. **Same-name drivers.** The trace directory uses the simple class name of the driver. Two
   drivers `a.Foo` and `b.Foo` write to the same directory and replay each other's traces.
3. **All-driver generation.** `./gradlew -p example test --tests '*InvariantCounterDriver*'`
   ran quint for all 8 example drivers, each time (the default seed is not pinned).

The assessment also found closed beads with gaps: qk-adm2 (spec not an input), qk-0vs7 (no
timeout on the Gradle path), qk-t281 and qk-eigq (`-Pquint.parallelism` has no effect on
generated tests), and qk-sa74 (no end-to-end test).

## Design

### Approach

Fix the Gradle plugin first, because B1 to B6 change the same files
(`GenerateQuintTracesTask.kt`, `QuintKonnectPlugin.kt`). Do these beads one after the other, in
the order of the dependencies. B7, B8 and B9 can start at any time.

The CLAUDE.md rule applies: a change to the Gradle plugin, `Driver`, the annotations or the
`-Pquint.*` properties must also update `skills/quint-konnect/`.

### Components

#### B1. `generateQuintTraces` ignores the spec content (qk-q5z8, bug, P1)

- Problem: the task inputs are the KSP manifests, the quint version, the overrides and
  `QUINT_SEED` (`gradle-plugin/.../GenerateQuintTracesTask.kt:96-123`). A manifest has the spec
  path, not the spec content. The task is `@CacheableTask` (`:89`). With a pinned seed, a spec
  change does not generate new traces, and the build cache can send old traces to other
  machines. The files that a spec imports are not inputs either.
- Approach: add an `@InputFiles @PathSensitive(RELATIVE)` property for the spec files. Set it
  from `extension.quintIrSpecs` (default `src/test/resources/**/*.qnt`, which also covers the
  imported files there) and from the spec path of each manifest.
- Acceptance: a new case in `GenerateQuintTracesFunctionalTest.kt` pins a seed, changes the
  spec, and expects the task to execute (not UP-TO-DATE, not FROM-CACHE). Update
  `docs/decisions/generate-quint-traces-task.md`.

#### B2. Drivers with the same simple name share one trace directory (qk-q6av, bug, P2)

- Problem: `GenerateQuintTracesTask.kt:161` uses `DriverManifest.simpleName` for the directory.
  `core/.../trace/TraceSource.kt` (`defaultTraceSource(testName)`) reads the same name. The
  generated suite sends `testName = <simple name>` (`ksp/.../generators/QuintSuiteGenerator.kt`).
  The result is false test failures. `docs/decisions/generate-quint-traces-task.md:28` says the
  change "wasn't made worse or better". This is not correct: before qk-adm2, the collision
  changed only the names of saved failure files.
- Approach: use the fully qualified driver name for the trace directory and for the files that
  `FailureTraceWriter` saves. Keep the simple name for display text.
- API changes: `core.api` changes if a public signature changes.
- Acceptance: a test with two drivers that have the same simple name in different packages.
  Each driver replays only its own traces. Correct the decision doc.

#### B3. A test run generates traces for all drivers (qk-blt0, feature, P2)

- Problem: `QuintKonnectPlugin.kt:177` and `:183` make every `Test` task depend on
  `checkQuint` and `generateQuintTraces`. The default seed is not pinned, so the task never is
  UP-TO-DATE. A `--tests` filter does not decrease the work. A `Test` task without drivers also
  needs quint.
- Approach (recommended, see Open Questions): make `generateQuintTraces` opt-in with a new
  extension flag (default off). Keep test-time generation (`TraceGenerator`) as the default. Do
  not add `checkQuint` to a `Test` task in a project without drivers.
- API changes: a new property in `QuintKonnectExtension`; `gradle-plugin.api`.
- Acceptance: a filtered `test` run starts quint only for the drivers that run. Add a
  functional test. Update README, AGENTS.md, the skill and the decision doc.

#### B4. No time limit for quint in `generateQuintTraces` and `quintIr` (qk-f78q, bug, P3)

- Problem: `execOperations.exec` has no time limit (`GenerateQuintTracesTask.kt:174`,
  `QuintIrTask.kt:73`). `TraceGenerator` has 10 minutes (`GeneratorConfig.timeout`). After
  qk-adm2, the default path lost this limit, against the intent of qk-0vs7.
- Approach: set the convention of the Gradle `Task.timeout` property to 10 minutes on both
  tasks.
- Acceptance: a test with a fake quint that does not stop. The build fails with a message that
  names the task.

#### B5. One quint command builder, or a parity test (qk-l2xg, chore, P3)

- Problem: `GenerateQuintTracesTask.buildCommand` (`:192`) is a copy of `RunConfig.toCommand`
  and `TestConfig.toCommand`. No test compares them. `escapeRegex`, `sanitizeFileName` and
  `sequenceNumber` have 2 or 3 copies each. `TraceGenerator` uses the first group of digits in a
  file name; `ItfFileTraceSource` and `TracesDirTraceSource` use the last group.
- Approach: add a parity test in `gradle-plugin` (with `:core` as a test dependency). It
  compares the two argument lists for the `run` and `test` kinds. Put the core helpers in one
  internal file. If B3 removes the Gradle path, do only the core part.

#### B6. Remove `Runner.runTest` and `-Pquint.parallelism` (qk-5fyu, chore, P3)

- Problem: no generated code calls `Runner.runTest`. The generators of 0.1.0 and 0.2.0 call
  `traceReplays`. `-Pquint.parallelism` changes only that path (`ReplayRunner.kt:30`, `:99`).
  For users, the property does nothing.
- Approach: remove `Runner`, the thread pool, the `PARALLELISM_*` properties and the batch-path
  buffer logic in `ConsoleReplayListener`. Change the users in `integration-tests` (for example
  `UnsafeCounterInvariantTest`) to `traceReplays`.
- API changes: breaking. Update `core.api` and `gradle-plugin.api`.
- Acceptance: `./gradlew build` and `./gradlew -p example build` pass. README, AGENTS.md and the
  skill do not name the removed options.

#### B7. Small doc and comment fixes (qk-g80c, chore, P3)

- `README.md:15` says that the library runs quint "at test runtime". With the plugin,
  `generateQuintTraces` runs quint before the tests.
- The README "Modules" row for `gradle-plugin` does not list trace generation, `quintIr` or
  `shrinkQuintTraces`.
- `AGENTS.md:102-104` tells you to search for `0.1.0` at each release. Make this text
  independent of the version.
- `core/.../ReplayRunner.kt:43-48` and `:72-78`: move the two comments to the declarations that
  they describe.

#### B8. Decide the `readSpecIr` default before 1.0 (qk-zu8a, task, P4)

- Problem: the main value of the library (generated types, spec checks) needs `readSpecIr`,
  but its default is `false` (`QuintKonnectExtension.kt`). The tests already need quint. The cost:
  `-Pquint.replay` then also needs quint
  (`docs/decisions/replay-needs-quint-with-read-spec-ir.md`).
- Output: a decision record in `docs/decisions/`. Change the default only if the decision
  accepts it.

#### B9. End-to-end test for replay with `readSpecIr` (qk-gb95, task, P3)

- Problem: qk-sa74 asked for this test. The current tests (`QuintIrFunctionalTest.kt:136`,
  `:165`) check only the task graph.
- Approach: add a functional test or a CI step. It compiles a `readSpecIr` project and replays
  a saved `.itf.json` file with `-Pquint.replay`.

### API Changes

- B2: `core.api` can change (driver name in trace lookup).
- B3: new `QuintKonnectExtension` property; `gradle-plugin.api`.
- B6: `Runner` and `-Pquint.parallelism` are removed. This is a breaking change.

## Testing Strategy

- Each bead adds the test that its acceptance criteria name.
- Each bead runs `./gradlew build` and `./gradlew -p example build` (quint 0.32.0 in `PATH`).
- For B1, do the manual test from Background again. The test must fail after the spec change
  without `--rerun`.

## Rollout Plan

- Release B1 to B4 in the next 0.x version.
- B6 is a breaking change. Mark its commit with a `BREAKING CHANGE:` footer, so git-cliff puts
  it in the release notes.
- At release, update the version in the skill, in README.md and in
  `.claude-plugin/plugin.json` (AGENTS.md "Releasing").

## Open Questions

- B3: make `generateQuintTraces` opt-in, or keep it and generate traces only for the drivers
  that run? This spec recommends opt-in, because Gradle cannot easily map a `--tests` filter to
  drivers.
- B6: keep `ReplayRunner.runTest` (sequential) for hand-written callers, or remove it?
- B8: make `readSpecIr = true` the default before 1.0?
